# Mediation — спецификация медиационного слоя

> Спецификация компонента. См. `ideal-agent-architecture.md` §3.4. Самодостаточна.

## 1. Назначение

Mediation — единственная точка, где выход модели становится состоянием системы. Ни один шаг с моделью не пишет в состояние, память, инструмент или пользователю напрямую: всё проходит контракт и политику. Это реализация инварианта I3 — «выход модели не становится состоянием без валидации».

Принцип заимствован из регулируемых отраслей: там между мощной, но непредсказуемой генеративной компонентой и формальным процессом ставится посредник, который пропускает дальше только соответствующие формальному контракту результаты. Здесь тот же приём применён ко всему агентному циклу.

## 2. Поток

```
выход модели (сырой текст)
   │
   ▼
┌──────────────┐   отказ   ┌─────────────────────────┐
│ 1. parse     │──────────▶│ повтор (до 2),           │
└──────┬───────┘           │ с подсказкой формата     │
       ▼                   └───────────┬─────────────┘
┌──────────────┐   отказ               │ после исчерпания
│ 2. schema    │───────────────────────┤
└──────┬───────┘                       ▼
       ▼                        эскалация: human_gate
┌──────────────┐   отказ         или падение шага
│ 3. policy    │────────────────▶ (без повтора: нарушение
└──────┬───────┘                  политики повтором не лечится)
       ▼
┌──────────────┐
│ 4. commit    │──▶ патч состояния / аргументы инструмента / ответ пользователю
└──────────────┘
Каждая стадия пишет событие: mediation.{parsed, validated, committed, rejected}
```

## 3. Контракты

- Контракт = тип данных со схемой: поля, типы, обязательность, перечисления, диапазоны, ограничения длины. Версионируется вместе с шагом процесса.
- Подсказка модели собирается из схемы автоматически (структурированный режим вывода); для слабых моделей добавляется пример из той же версии контракта.
- **Схема живёт в коде, а не в подсказках:** подсказка генерируется из контракта, а не контракт угадывается из текста подсказки.

Пример контракта (нейтральная нотация):

```
ClassificationOut:
  category: enum[billing, card, debt, other]   # обязательное
  risk:     integer, min 0, max 10             # обязательное
  summary:  string, max_length 280             # обязательное
  # поля сверх перечисленных — запрещены
```

## 4. Стадии

### 4.1. Parse

Извлечение данных из сырого вывода: толерантно к оформительским обёрткам (markdown-блоки), но без «умного» угадывания смысла. Неразобранное = повтор, а не эвристика: эвристический разбор — скрытый источник невоспроизводимости.

### 4.2. Валидация схемой

Строгая: типы, обязательные поля, перечисления, диапазоны, максимальные длины, и — принципиально — **запрет неизвестных полей**. Если модель добавила поле сверх контракта, это отказ. Причина: внедрённые в контекст инструкции часто провоцируют модель эмитировать «служебные» поля («подтверждено», «пропустить проверку»); закрытая схема делает такую инъекцию бесполезной.

### 4.3. Проверка политики (детерминированная, без моделей)

- Межполевые правила: `risk >= 7 → category != "other"`.
- Ссылки на состояние: идентификатор из выхода должен существовать в состоянии, иначе отказ (модель не может «придумать» объект).
- Лимиты: суммарная длина, число вызовов инструментов на шаг.
- Контроль утечек: если в выходе обнаружено значение секрета — событие безопасности, шаг падает, процесс эскалирует. Это четвёртая точка маскировки в дополнение к трём границам данных (аргументы/вывод инструментов, мост к хранилищу, тексты подтверждений).

### 4.4. Commit

- В состояние — патч с метаданными: версия контракта, идентификатор и класс модели.
- В инструмент — аргументы только из валидированного объекта, никогда из сырого текста модели. Это закрывает целый класс внедрений в аргументы инструментов.
- Пользователю — только поля, помеченные в контракте как публикуемые.

## 5. Повторы и эскалация

| Случай | Повтор | Эскалация |
|--------|--------|-----------|
| Неразобранный вывод | 2, с подсказкой формата | человек / падение шага |
| Ошибка схемы | 2, в подсказку добавляется текст ошибки валидации | человек / падение шага |
| Нарушение политики | 0 (повтор не лечит) | человек |
| Попытка утечки секрета | 0 | падение процесса + событие безопасности |
| Модель деградировала | переключение по заранее заданной цепочке провайдеров класса (см. `ideal-agent-architecture.md` §3.10), затем эскалация | человек |

Все правила эскалации — код. Пути «модель решила спросить человека» не существует.

## 6. Телеметрия (вход для оценки)

События Mediation — основной источник метрик здоровья моделей и процессов:

- **Доля отказов** по (процесс, шаг, модель, версия контракта).
- Рост отказов после смены версии модели = деградация → событие контура здоровья навыков.
- Доля шагов, дошедших до второго повтора, = индикатор «контракт слишком сложен для класса модели» → правило для оценщика бюджета контекста.
- Офлайн-замер доли отказов на золотом наборе — быстрый предиктор онлайн-качества: практика показывает, что качество офлайн-оценки коррелирует с онлайн-результатом, и это нужно использовать, а не переизмерять в бою.

## 7. Границы

- Mediation **не проверяет смысл** — только форму и политику. Семантические ошибки ловятся оценочным циклом и человеческим контролем на риск-ветках. Проверка смысла второй моделью сознательно исключена: слабому звену нельзя доверять проверку сильного, а сильное звено делает систему зависимой от внешнего провайдера на каждом шаге.
- Mediation **не заменяет Capability**: контракт валиден, но вызов деструктивен — работает статический запрет и подтверждение независимо.
- Для шагов генерации кода Mediation валидирует **результат выполнения программы** (финальное значение), а не сам код; код ограничивается изолированной средой (см. `executors.md`).

## 8. Точки встраивания в систему

| Где применяется | Как |
|-----------------|-----|
| Шаги процесса с моделью | обязательно, до применения патча |
| Фоновые работники памяти (извлечение, сжатие, дедупликация) | тот же интерфейс: они — частный случай «модель + контракт» |
| Свободный режим (agent_step) | валидация результата при записи в состояние процесса |
| Ответы пользователю | только публикуемые поля контракта |
