# Идеальная агентная система

> Архитектурный документ. Самодостаточен: не требует знакомства с другими проектами, продуктами или внешними источниками.

## 0. Философия системы

Идеальная агентная система — это не «умная модель с инструментами», а **детерминированная операционная среда, в которую модели встроены как исполнители рутины**. Модель никогда не решает, куда пойдёт задача, что попадёт в контекст и что запишется в память. Модель извлекает, суммаризирует, транслирует неструктурированное в структурированное — и её выход валидируется контрактом, прежде чем стать состоянием.

Три независимых наблюдения, на которых стоит этот принцип:

1. **Промышленная практика.** Команды, доведшие агентов до реальной эксплуатации с миллионами пользователей, сходятся в одном: задачи, которые можно заранее разложить на шаги, выполняются надёжнее и дешевле предопределёнными конвейерами, чем свободным агентом. Свободный агент оправдан только там, где план нельзя написать заранее.
2. **Эволюция инструментов.** Зрелые платформы построения агентов пришли к модели конечного автомата с состоянием, а не к «свободному диалогу модели с инструментами»: предсказуемость, тестируемость и восстановление после сбоев важнее гибкости маршрутизации.
3. **Аварийный опыт.** Анализ отказов агентных систем показывает: катастрофические классы дефектов — потеря задач при сбое, гонки конкурентного доступа, обход ограничений через неочевидный вход — живут в инфраструктуре и доверии к входным данным, а не в качестве рассуждений модели. Значит, надёжность нужно строить кодом вокруг модели, а не ожидать её от модели.

## 1. Инварианты (нарушать нельзя)

| # | Инвариант | Суть |
|---|-----------|------|
| I1 | Решения принимает детерминированный код | Маршрутизация задач, отбор контекста, ветвление процесса, запись в память, политики доступа — только код. Модель — исполнитель: извлечь, суммаризировать, трансформировать, сгенерировать фрагмент. «Модель решает маршрутизацию» — красный флаг архитектурного ревью |
| I2 | Молчаливой мутации нет | Любое изменение навыка, конфигурации или устойчивого состояния происходит через событие и подтверждение человека. Система никогда не переписывает сама себя без следов |
| I3 | Выход модели не становится состоянием без валидации | Между генерацией и записью стоит контракт: схема данных плюс детерминированные правила. Невалидный выход отклоняется до commit |
| I4 | Секреты недоступны модели | Модель видит только алиасы («токен платёжного шлюза»), никогда — значения. На всех границах данных стоит маскировщик |
| I5 | Один самодостаточный артефакт | Система развёртывается одним исполняемым артефактом с минимумом внешних зависимостей. Хранение — встраиваемое: журнал событий на ключ-значение, полнотекстовый индекс, векторный индекс. Внешние СУБД не требуются |
| I6 | Деструктивное блокируется кодом до выполнения | Статический анализ действия до его запуска; если действие в запретном классе — оно блокируется безусловно, и подтверждение человека не может это отменить |
| I7 | Каждый шаг воспроизводим | Журнал событий плюс снапшоты состояния позволяют воспроизвести любой прогон без участия моделей: состояние — это свёртка событий |
| I8 | Без «этического модуля» | Отказы не порождаются рассуждением модели о морали. Отказы — явный код: запретные таблицы, политики, тесты. Поведение системы объяснимо и проверяемо |

## 3. Компоненты

### 3.1. Process Engine — детерминированный остов

Сердце системы. Задача описывается процессной моделью: направленным графом шагов с типами `Sequential / Parallel / Loop / Branch / HumanGate / AgentStep` и исполнительскими типами `tool / llm_structured / codeact`.

- **Шаг** — программный интерфейс: получает состояние на чтение, возвращает патч состояния или ошибку. Шаг не знает о моделях; если ему нужна модель, он вызывает исполнителя через Mediation.
- **Состояние** — иммутабельный документ в журналируемом хранилище; каждый шаг возвращает патч, движок применяет его атомарно и пишет событие.
- **Ветвление** — только код на валидированных данных: `если риск > 7 → шаг человеческого контроля`. Модель никогда не выбирает ветку.
- **Процессные модели** — декларативны, версионируются, хранятся рядом с навыками; изменение версии — событие с подтверждением.
- **Снапшот** — автоматически перед каждым мутирующим шагом.

Набор типов намеренно ограничен: предсказуемый, целиком тестируемый набор композиции важнее выразительности. Произвольный граф, который модель дорисовывает на ходу, не тестируется в принципе.

### 3.2. Agent Loop — люк для открытых задач

Для задач, не ложащихся в процессную модель («исследуй», «разберись и почини»).

- Цикл «рассуждение → действие → наблюдение» с опциональными стратегиями: самокритика после шага, цикл «предложи — выполни — проверь вердиктом».
- **Вход в режим — детерминирован:** явный запрос пользователя, команда или шаг типа `AgentStep` в процессной модели. Никогда — решением модели.
- **Ограничения:** максимум ходов, снапшот перед каждой правкой, подтверждения по политике инструментов, бюджет токенов.
- Выход из цикла — финальный ответ, таймаут или отрицательный вердикт проверки; результат проходит Mediation, если пишется в состояние.

### 3.3. Executors — исполнители шагов

| Исполнитель | Когда | Принцип |
|-------------|-------|---------|
| **Structured LLM** | Узкий шаг: извлечь, классифицировать, суммаризировать, перевести | Контракт схемы данных; выход валидируется до записи |
| **CodeAct** | Шаг с вычислениями, итерациями по данным, композицией вызовов | Модель пишет программу → изолированное выполнение → логи в состояние шага |
| **Tool-only** | Шаг без семантики: прочитать, записать, получить из внешней системы | Без модели вообще |

Почему генерация кода как действие, а не вызов инструментов по одному: программа естественно выражает циклы, условия и композицию — одно действие вместо пяти обращений к модели. Независимые замеры показывают, что именно в этом режиме модели с открытыми весами догоняют проприетарные: им проще писать код, чем эмитировать строгие JSON-вызовы. Для системы с локальным инференсом это режим паритета.

### 3.4. Mediation — медиационный слой

Единый интерфейс между любым выходом модели и состоянием системы.

```
выход модели → разбор → валидация схемой → проверка политики → commit в состояние
                  ↓ отказ
              повтор (до 2) → эскалация к человеку / падение шага
```

- Схемы версионируются вместе с шагом процесса; подсказка модели собирается из схемы, а не пишется вручную.
- Проверка политики — детерминированная (диапазоны, перечисления, межполевые правила), никогда «модель проверяет модель».
- Каждый отказ — событие с причиной: это данные для оценки качества и детектор деградации модели.

### 3.5. Context Engine — отбор контекста кодом

- **Маршрутизатор** — правила в коде: класс задачи → набор слоёв контекста.
- **Сборщик** — фиксированный порядок слоёв: системные правила → личность → проект → навыки → факты → сессия → текущая задача.
- **Оценщик** — класс способностей модели определяет бюджет и минимальный вес слоёв: слабая модель получает более короткий и более структурированный контекст.
- **Фоновые работники** — извлечение фактов из диалога, сжатие истории, дедупликация, консолидация. Каждый работник — частный случай пары «модель + Mediation»: генерация по схеме с повторами при невалидности.

### 3.6. Память — четырёхслойная

| Слой | Содержимое | Кто пишет |
|------|------------|-----------|
| **Рабочая** | состояние процесса/сессии, промежуточные результаты | движок (патчи) |
| **Эпизодическая** | сессии, события шагов, решения, отчёты — журнал навсегда | движок (события), никогда модель напрямую |
| **Семантическая** | факты, предпочтения, уроки; гибридный поиск: векторный + полнотекстовый | только через дедупликацию и валидацию |
| **Процедурная** | навыки в виде документов: описания всегда доступны, полные тела — по требованию | только через подтверждение человека |

Принцип: запись в память — только через дедупликацию и контракт; чтение — только через Context Engine. Модель никогда не решает, что помнить и что вспомнить.

### 3.7. Capability & Safety — защита до выполнения

1. **Безусловный запрет (deny-статика):** статический анализ действия до запуска — разрушение файловых систем, запись на блочные устройства, эскалация привилегий, fork-бомбы, удаление вне рабочей области. Подтверждение человека не отменяет deny (I6).
2. **Гейты подтверждения:** у каждого инструмента объявлено, требует ли действие подтверждения; режимы: умный (правила риска в коде) / всё вручную / выключено (только изолированные профили).
3. **Сетевой гейт:** обращения к приватным адресам — только через подтверждение (защита от подделки запросов к внутренним сервисам).
4. **Маскировщик секретов:** на всех границах данных — аргументы и вывод инструментов, мост к хранилищу, тексты подтверждений, запись в память. Модель видит алиасы (I4).
5. **ACL плагинов:** манифест объявляет, какие события плагин может публиковать и к каким секретам имеет доступ; манифест — статический файл, который сам плагин переопределить не может.
6. **Шаг человеческого контроля:** обязательный тип шага процессной модели; эскалация по риску или ошибке валидации — детерминированная.
7. **Аварийная остановка:** заморозка всех акторов за ограниченное время с постановкой активных задач обратно в очередь.

### 3.8. Actors & Scheduler — мультиагентность без маршрутизации моделью

- **Актор** = процессная модель + своя память (профиль типа `actor`, см. `memory-model.md` §5) + почтовый ящик. Коммуникация — конверты через шину событий.
- **Диспетчер** — доска задач: назначение акторам по декларативным правилам в коде; после заданного числа неудач задача блокируется и уходит человеку. **Лимит очереди подтверждений:** диспетчер ограничивает число одновременных `human_gate`-эскалаций на арендатора/очередь; при достижении предела новые задачи, ведущие к эскалации, не назначаются, а расписания, упирающиеся в необработанные `human_gate`, помечаются `throttled`, а не отменяются и не тикают вхолостую (см. `process-engine.md` §5).
- **Планировщик** — расписания с защитой от двойного срабатывания; невозможное расписание отклоняется при создании, а не «тикает вечно».
- **Никакого оркестратора-модели:** координация — топология процессной модели и правила диспетчера. Маршрутизация моделью — главный документированный источник эмерджентных сбоев мультиагентных систем: бесконечные взаимные вызовы, блокировки, противоречивые решения.

### 3.9. Инструменты и протоколы

- Встроенные наборы: терминал, файлы, система контроля версий, web (с сетевым гейтом), снапшоты, память, навыки, поиск по сессиям, список задач, доска, планировщик.
- **Унифицированный протокол инструментов — двунаправленный:** система выступает клиентом внешних серверов инструментов и сама отдаёт свои инструменты, ресурсы и шаблоны наружу по тому же протоколу. Единый стандарт интеграции вместо собственного адаптера под каждый сервис.
- Плагины-коннекторы — изолированные процессы с межпроцессным RPC, манифестами и ограниченными доступами.
- **Граница инварианта I5:** самодостаточность гарантирована для ядра — Process Engine, Mediation, Capability, Context Engine, память. Ядро не имеет обязательных внешних зависимостей и разворачивается одним артефактом без установленных плагинов. Плагины — опциональное расширение за этой границей: им разрешено обращаться к произвольным внешним системам, но (а) без плагина система полнофункциональна на встроенных наборах, (б) недоступность или отказ плагина не останавливает ядро — падает только шаг, который его использует. I5 — про автономность ядра, а не про запрет любых внешних систем в развёртывании.

### 3.10. Model Pool

- Пул локального инференса и удалённых провайдеров с проверкой здоровья и событием деградации.
- **Классы способностей (tiers):** класс модели определяет бюджет контекста, лимиты ходов и допуск к исполнителям: слабый класс — только структурированные шаги, генерация кода — сильным классам или с явным разрешением в процессе.
- **Присвоение класса — код, не самооценка модели.** Класс — поле реестра моделей: стартовое значение задаётся вручную при регистрации (паспорт модели от провайдера), дальше переопределяется офлайн-оценкой на золотом наборе (§3.11) — доля отказов валидации и доля успешных шагов CodeAct на контрольных задачах. Понижение класса — автоматическое событие при деградации метрик, применяется сразу. Повышение класса — только через подтверждение человека (I2): рост метрик — повод для ревью, не для тихого автоапгрейда допуска.
- **Выбор провайдера внутри класса — код по декларативной политике, не запрос к модели.** Среди провайдеров, удовлетворяющих минимальному классу шага, селектор применяет одно настраиваемое правило пула: предпочтение локального инференса при равном классе (нулевая предельная стоимость, данные не покидают периметр); иначе — наименьшая стоимость токена среди удалённых при соблюдении латентность-бюджета шага; либо явный фиксированный порядок предпочтения в конфигурации. Правило одно на пул или переопределяется на уровне процесса — «какого провайдера предпочитаешь» никогда не вопрос к модели.
- **Бюджет стоимости — рядом с бюджетом токенов.** Процесс может объявить не только `token_budget`, но и `cost_budget` (в условных единицах через прайс-таблицу реестра моделей — код-данные, не то, что сообщает о своей стоимости сама модель). Достижение `cost_budget` — детерминированный прерыватель наравне с `max_steps`/`timeout` (см. `process-engine.md` §2, §4): шаг падает или эскалирует по политике процесса, дальнейшие вызовы дорогих провайдеров не производятся.
- **Латентность — SLA шага, не приоритет пула по умолчанию.** У шага есть необязательное поле `latency_budget`; провайдер, чья измеренная (не заявленная) латентность за скользящее окно превышает бюджет, исключается из выбора для этого шага без события деградации — это несоответствие профилю задачи, а не сбой. Событие деградации возникает только когда провайдер выпадает из бюджета латентности для всех шагов класса, которым раньше удовлетворял.
- **Отказоустойчивое переключение — заранее заданная цепочка, не импровизация в момент сбоя.** Для каждого класса — упорядоченная цепочка провайдеров, сконфигурированная заранее (ссылка из `mediation.md` §5, строка «модель деградировала»); переключение идёт по цепочке при недоступности или деградации, событие на каждый переход; исчерпание цепочки — эскалация к человеку, а не молчаливое понижение класса шага.
- Замена модели не меняет поведение системы — меняется только качество исполнения шагов. Прямое следствие I1.

### 3.11. Eval & Observability

- **Трассировка:** каждый шаг — событие; любой прогон воспроизводится из журнала.
- **Двухцикловая разработка:** быстрый цикл — офлайн-оценка процессных моделей на золотых наборах (доля веток, доля отказов валидации); медленный — онлайн-метрики (доля успешных задач, скорость подтверждений, отказы медиации). Качество офлайн-оценки должно предсказывать онлайн-результат — это проверяемая гипотеза, а не вера.
- **Контур здоровья навыков:** устаревание навыка детектируется по росту отказов валидации и неиспользованию — событие и очередь ревью человеком; никогда молчаливая правка.

## 4. Жизненный цикл задачи

```
1. Intake:  поверхность → событие «новая задача»; класс задачи определяет код-маршрутизатор
2. Route:   правила → процессная модель ИЛИ свободный режим (явный люк)
3. Plan:    для процесса — инстанциация модели процесса; для люка — план стратегии
4. Цикл по шагам:
   - Context Engine собирает контекст (код)
   - Исполнитель: structured / codeact / tool-only
   - Mediation: контракт → политика → commit | повтор | эскалация
   - Capability: deny/подтверждение перед любым мутирующим вызовом
   - Событие: шаг зафиксирован, снапшот при мутации
5. Finish:  результат → память через дедупликацию → отчёт поверхности
6. Learn:   метки офлайн-оценки; здоровье навыков по факту деградации
```

## 5. Что код решает, а что модель

| Решение | Кто | Почему |
|---------|-----|--------|
| Маршрутизация задачи | Код (правила) | Ошибка классификации моделью неявна и не воспроизводима |
| Ветвление в процессе | Код (на валидированных данных) | Аудит и воспроизводимость |
| Отбор контекста | Код (маршрутизатор/сборщик/оценщик) | Детерминизм и бюджет |
| Запись в память | Код (дедупликация) | Защита от отравления памяти |
| Допуск к выполнению | Код (capability) | Безусловность deny |
| Извлечение сущностей из текста | Модель + Mediation | Зона силы модели |
| Суммаризация, переписывание | Модель + Mediation | Зона силы модели |
| Генерация программы шага | Модель в изолированной среде | Зона силы модели, изолированная |
| Открытое исследование (люк) | Модель, ограниченная лимитами | Осознанное исключение |

## 6. Обоснование ключевых решений

| Решение | Обоснование |
|---------|-------------|
| Процессный остов вместо свободного агента | Оценочная матрица по критериям детерминизма, работы со слабыми моделями, безопасности и стоимости даёт остову максимум; промышленные внедрения подтверждают: конвейеры предсказуемы, свободные агенты — нет |
| Исполнитель через генерацию кода | Код композитнее одиночных вызовов; в этом режиме открытые модели достигают паритета с проприетарными; меньше обращений к модели на многошаговых задачах |
| Контрактная валидация (Mediation) | Слабая модель не может «протащить» невалидный выход дальше шага; каждый отказ — данные для оценки; аргументы инструментов никогда не берутся из сырого текста модели |
| Отказ от оркестратора-модели | Маршрутизация моделью — нарушение I1 и главный источник эмерджентных сбоев координации |
| Навыки как процедурная память | Повторяемые процедуры должны жить в версионируемых документах, а не в истории диалога; описания всегда доступны, тела — по требованию (экономия контекста) |
| Двунаправленный протокол инструментов | Единый стандарт подключения внешних систем устраняет зоопарк адаптеров |
| Двухцикловая оценка | Быстрые офлайн-итерации по золотым наборам, медленные архитектурные решения по онлайн-метрикам |
| Снапшоты + подтверждения | Откат независимо от системы контроля версий; деструктивное над внешними системами снапшотами не покрывается — только подтверждением |
| Четырёхслойная память | Рабочая/эпизодическая/семантическая/процедурная — разделение по времени жизни и доверию |

## 7. Чего в системе сознательно нет

- **Оркестратора-модели и маршрутизатора-модели** — нарушение I1, источник эмерджентных сбоев.
- **Проверки «модель судит модель»** — слабому звену нельзя доверять проверку; валидация только контрактом и кодом.
- **Этического модуля** — инвариант I8; отказы — явный код и запретные таблицы.
- **Внешних СУБД и обязательных сервисов** — I5; всё хранение встраиваемое.
- **Скрытых каналов самоизменения** — любое изменение системы только через событие и подтверждение (I2).

## 8. Этапы внедрения

| Этап | Содержание | Результат |
|------|------------|-----------|
| 1 | Mediation как единый интерфейс: схемы, валидация, повторы, телеметрия отказов | Ни один выход модели не пишется напрямую |
| 2 | Process Engine: граф шагов, иммутабельное состояние, восстановление из журнала, шаги человеческого контроля | Структурированные задачи выполняются без свободного агента |
| 3 | CodeAct-исполнитель: изолированная среда, статическая проверка программы перед запуском, стабы инструментов через capability-гейты | Вычислительные шаги на паритете даже со слабыми моделями |
| 4 | Оценочный стенд: золотые наборы, офлайн-метрики веток и отказов, связка с онлайн-метриками | Доказуемая корреляция офлайн-оценки и онлайн-результата |
| 5 | Протокольный сервер инструментов наружу | Система — источник инструментов для внешних потребителей по единому стандарту |

Основание — шина событий, хранилище, capability-слой, память, плагины — предполагается уже существующим; этапы 1–5 строят верхний слой, не ломая инвариантов.

## 9. Навигация по спецификациям

- `process-engine.md` — модель процесса, типы шагов, состояние, восстановление, тестирование.
- `mediation.md` — контракты, стадии, повторы и эскалация, телеметрия.
- `executors.md` — исполнители шагов, изолированное выполнение кода, допуски по классам моделей.
- `memory-model.md` — слои памяти, правила записи и чтения, изоляция.
- `security-model.md` — модель угроз, слои защиты, режимы подтверждений, аудит.
- `deployment.md` — развёртывание и обновление через npm + GitHub, доверенный список репозиториев, пайплайн сборки и тестирования.
- `stack.md` — обоснованный выбор конкретных технологий: Rust-ядро, SQLite как единое хранилище, Wasmtime для CodeAct, MCP, npm-bootstrap.
- `views/` — диаграммный слой: системная/компонентная/данных/сетевая архитектуры (C4) плюс runtime-, state-, security-view, quality attributes, domain glossary, risks & debt.
