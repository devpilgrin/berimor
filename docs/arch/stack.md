# Technology Stack — обоснованный выбор технологий

> Решение о конкретных технологиях. См. `ideal-agent-architecture.md` (инварианты I1–I8) и `deployment.md`. Как и `deployment.md`, этот документ называет конкретные технологии — это осознанный выбор, а не спецификация принципа; при появлении причины сменить конкретную технологию сам принцип (какие свойства она обязана обеспечивать) не меняется.

## 1. Принцип подбора

Стек выбирался под три требования архитектуры, которые сильнее всего ограничивают пространство вариантов:

1. **I5 (один самодостаточный артефакт)** — приоритет embedded-решениям над клиент-серверными (встроенная БД вместо внешней, встроенный движок песочницы вместо внешнего рантайма, встроенный планировщик вместо очереди).
2. **I6 (деструктивное блокируется кодом до выполнения)** — приоритет технологиям, где изоляция структурная (недоступность ОС/сети из песочницы физически, на уровне рантайма), а не спискового типа (блок-лист, который нужно не забыть обновить).
3. **Кросс-платформенная поставка через GitHub Releases** (`deployment.md` §7) — приоритет технологиям с надёжной кросс-компиляцией в один статический бинарник без необходимости в C/C++ тулчейне на каждой целевой платформе.

## 2. Ядро: язык рантайма

**Rust** — для всего детерминированного ядра (Process Engine, Mediation, Context Engine, Capability, Actors/Scheduler, слой хранения, хост CodeAct-песочницы).

| Критерий | Rust | Go (рассмотрен) |
|---|---|---|
| Хост для WASM-песочницы | `wasmtime` — индустриальный стандарт для запуска недоверенного кода (JIT на Cranelift, лимиты по «топливу» и памяти) | `wazero` — чистый Go без cgo, проще собрать, но интерпретация медленнее на вычислительно тяжёлых шагах CodeAct |
| Контракты Mediation | типы + `serde` дают схему как часть типов компиляции; `schemars` генерирует JSON Schema из тех же типов — «схема живёт в коде» в буквальном, а не декларативном смысле | достижимо через reflection-валидацию, но схема и Go-структура — два синхронизируемых источника правды |
| Единый статический бинарник | достижим (rusqlite в режиме `bundled` линкует SQLite статически, `rustls` вместо OpenSSL убирает системную зависимость) | достижим нативно, обычно даже проще |
| Секреты как тип (I4) | обёрточный тип секрета, не реализующий `Display`/`Debug` с утечкой значения — утечка ловится на этапе компиляции, а не ревью | нет эквивалентного гарантированного на уровне типов механизма |
| Скорость разработки/порог входа | выше | ниже |

Решающий фактор — `wasmtime` для CodeAct и типобезопасные контракты для Mediation: обе линии архитектуры получают более сильные, встроенные в компилятор гарантии, а не соглашения, которые нужно проверять отдельно.

**Не выбраны для ядра:** Python/Node.js как основной рантайм — оба требуют либо тяжёлого рантайма в каждом платформенном артефакте (Node — сотни МБ), либо GIL-ограничений на конкурентность акторов (Python); оба хуже подходят для структурной (не списковой) песочницы.

## 3. Хранилище — Memory Model и состояние Process Engine

**SQLite, один файл, единый движок для всех структур хранения**, вместо отдельной БД под каждый вид данных из `memory-model.md`:

| Требование архитектуры | Механизм SQLite |
|---|---|
| Журнал событий (KV) на ключ-значение | таблица `events(seq, kind, payload, ts)`, append-only, WAL-режим — один писатель на инстанс процесса, как того требует `process-engine.md` §4 |
| Полнотекстовый индекс (эпизодическая память) | встроенное расширение `FTS5` |
| Векторный индекс (семантическая память, гибридный поиск) | расширение `sqlite-vec` — векторный поиск в том же файле, без отдельного векторного хранилища и синхронизации между двумя БД |
| Граф сущностей (опциональный слой) | таблицы `nodes`/`edges` в том же файле; обходы — рекурсивные CTE, без отдельной графовой СУБД |
| Снапшоты состояния | материализованная таблица `snapshots(process_id, seq, state_blob)`, консистентна с журналом в той же транзакции |

Один встроенный движок для событий, полнотекста, векторов и графа — это не только про I5: гибридный поиск (§ памяти) требует объединять векторные и полнотекстовые результаты, и держать их в одной транзакционной БД проще и надёжнее, чем поддерживать консистентность между двумя разными хранилищами.

**Не выбраны:** PostgreSQL+pgvector — сильная связка, но внешний сервис, прямое нарушение I5; специализированные векторные БД — тот же довод плюс лишний процесс, которым нужно управлять при обновлении (`deployment.md`).

## 4. CodeAct — изолированное исполнение

**Wasmtime + JS-подмножество, компилируемое в WASM через встроенный QuickJS**, как основной путь.

- Модель пишет программу на ограниченном подмножестве JS (широко представлено в обучающих данных моделей, что важно для качества генерации у слабых классов — `executors.md` §4.1).
- Перед исполнением — статическая проверка исходника (парсинг + белый список идентификаторов): `eval`, `Function`, динамический `import`, глобальные сетевые объекты запрещены на уровне разбора текста программы, до компиляции в WASM — это первый барьер `executors.md` §4.2.
- Второй барьер — структурный: внутри WASM linear memory нет доступа ни к файловой системе, ни к сети в принципе, единственный канал наружу — явно экспортированные host-функции (стабы инструментов). Это делает первый барьер защитой от шума, а не единственной линией обороны.
- Лимиты — `wasmtime`-метрика «топлива» (детерминированный лимит по числу инструкций вместо недетерминированного wall-clock таймаута) + лимит linear memory + счётчик вызовов host-функций на программу.

**Рассмотрен и отклонён как основной путь:** Python в WASM (Pyodide-подобная сборка) — эргономичнее для моделей, обученных преимущественно на Python-коде, но тяжелее по времени холодного старта и размеру артефакта; оставлен как конфигурируемый профиль для доменов с тяжёлыми числовыми вычислениями, где выигрыш в качестве генерации перевешивает стоимость старта.

## 5. Model Pool

- **Локальный инференс:** `llama.cpp` (через Rust-биндинги) для GGUF-весов — встраивается в процесс без отдельного сервера инференса, кросс-платформенно (CPU и GPU-бэкенды), удовлетворяет I5 для локального класса моделей.
- **Удалённые провайдеры:** тонкий типизированный HTTP-клиент на провайдера за общим интерфейсом Model Pool — без фреймворка оркестрации моделей: маршрутизация и допуск по классам — код `ideal-agent-architecture.md` §3.10, а не логика библиотеки.
- **Эмбеддинги для семантической памяти:** компактная embedding-модель через тот же `llama.cpp`-бэкенд — запись факта не требует сетевого вызова к внешнему провайдеру только ради вектора.

## 6. Протокол инструментов

**MCP (Model Context Protocol)** как конкретная реализация требования §3.9 «унифицированный протокол — двунаправленный»: система одновременно клиент внешних серверов инструментов и сервер собственных инструментов/ресурсов/шаблонов по тому же стандарту. Это готовый открытый протокол именно с такой двунаправленной формой, а не абстракция, которую пришлось бы проектировать с нуля.

## 7. Actors & Scheduler

- Акторы — задачи `tokio` (асинхронный рантайм Rust), почтовые ящики — ограниченные асинхронные каналы; конверт считается доставленным только после фиксации в журнале SQLite — падение процесса между «отправлено» и «записано» не теряет сообщение (то же свойство отказоустойчивости, что и у Process Engine).
- Планировщик — не внешний cron/очередь, а min-heap ближайших срабатываний, персистентный в той же БД, проверяемый таймером `tokio`. Один движок хранения на весь стек, как и в §3.

## 8. Bootstrap-слой (npm)

**TypeScript, минимум зависимостей** — только определение платформы (`process.platform`/`process.arch`, встроено в Node, без пакетов), загрузка и атомарная распаковка артефакта (`node:crypto`/`node:fs`/`fetch`, системный `tar`/`Expand-Archive` — ни одной новой npm-зависимости, ROADMAP D3). Проверка подписи не дублируется на JS: bootstrap вызывает подкоманду верификации того же Rust-бинарника (`agent verify <file>`), а не переизобретает криптографию на другом языке — одна реализация проверки, не две за которыми нужно следить синхронно. Исключение — первая установка (ещё нет доверенного бинарника, который мог бы проверить сам себя): она сверяется по SHA-256, пришпиленному в сам npm-пакет на этапе публикации (`bootstrap/src/checksums-manifest.ts`) — не подпись и не крипто-проверка идентичности подписанта, простое сравнение хэша константного времени.

Минимальность зависимостей здесь — не стилистика, а прямое соответствие `deployment.md` §9: чем меньше пакетов подключено на этапе `npm install`, тем меньше поверхность атаки через скомпрометированную транзитивную зависимость до того, как вообще что-то верифицировано.

## 9. Сборка и подпись (CI)

| Стадия `deployment.md` §7 | Технология |
|---|---|
| Кросс-компиляция матрицы ОС×архитектура | Нативные раннеры GitHub Actions под каждую цель (`ubuntu-latest`, `ubuntu-24.04-arm`, `macos-latest`, `windows-latest`), не `cargo-zigbuild` с одного раннера — `cargo-zigbuild` не имеет практической поддержки цели macOS без `osxcross` и извлечения Apple SDK, что юридически спорно для редистрибуции; решение и обоснование зафиксированы в `.github/workflows/release.yml` (ROADMAP D1, реализовано) |
| Аудит зависимостей | `cargo-audit` / `cargo-deny` (лицензии и известные уязвимости) |
| Подпись артефактов | `sigstore`/`cosign`, keyless-подпись, идентичность подписанта — сам GitHub Actions workflow, приватный ключ нигде не хранится файлом |
| Провенанс npm-пакета | `npm publish --provenance` — встроенная в npm привязка пакета к конкретному запуску CI |
| CI-платформа | GitHub Actions — совпадает с уже выбранным хостингом релизов, без дополнительной системы CI |

## 10. Итоговая карта

| Компонент архитектуры | Технология | Причина в одной фразе |
|---|---|---|
| Process Engine, Mediation, Capability, Context Engine | Rust | типобезопасные контракты, единый бинарник, embedding `wasmtime` |
| Хранилище (все 4 слоя памяти + состояние) | SQLite + FTS5 + sqlite-vec | один встроенный движок вместо нескольких синхронизируемых |
| CodeAct-песочница | Wasmtime + JS-подмножество в WASM | структурная изоляция, а не списковая |
| Локальный инференс | llama.cpp (GGUF) | встроен в процесс, без внешнего сервера |
| Протокол инструментов | MCP | готовый двунаправленный стандарт |
| Акторы/планировщик | tokio + та же SQLite | без внешнего брокера/очереди |
| Bootstrap | TypeScript (минимальный) | совпадает с уже выбранной npm-дистрибуцией |
| Подпись/провенанс | sigstore/cosign, npm provenance | keyless, без хранимых приватных ключей |

## 11. Что сознательно не выбрано

- **Внешние СУБД, брокеры сообщений, векторные сервисы** — прямое нарушение I5 независимо от их качества как продуктов.
- **Тяжёлые ML-фреймворки в рантайме** (полноценные питоновские стеки инференса) — оправданы для обучения и офлайн-оценки (§3.11 главного документа), но не для поставляемого артефакта: офлайн-инструменты эволюции/оценки могут жить отдельно от того, что подпадает под I5, поскольку инвариант ограничивает развёртываемую систему, а не инструментарий её разработки.
- **Списковая (denylist) изоляция CodeAct** без структурного барьера — списки устаревают быстрее, чем их успевают обновлять; выбран рантайм, где отсутствие доступа — свойство архитектуры процесса, а не результата проверки.
