# Architecture Views — диаграммный слой архитектуры

Документы `arch/*.md` описывают архитектуру текстом — принципы, инварианты, контракты. Здесь те же решения представлены как диаграммы и структурированные представления (views), нужные непосредственно для написания системы. Ничего нового не решается — каждый документ ссылается на первоисточник в `arch/*.md` и `ADR/*.md`.

Организация — по двум опорным, не привязанным к вендору моделям: структурные диаграммы (система/компоненты) — в терминах **C4** (Context → Container → Component); остальные представления — категории, устоявшиеся в **arc42/4+1** (runtime view, data view, deployment/network view, quality attributes, risks). Это словарь для организации материала, не технология и не требование к реализации.

## Состав

| Документ | Вид (view) | Отвечает на вопрос |
|---|---|---|
| `system-architecture.md` | C4: Context + Container + Deployment | Что это за система, с чем граничит, из каких развёртываемых единиц состоит и где физически исполняется |
| `component-architecture.md` | C4: Component | Из каких внутренних модулей состоит ядро и как они связаны |
| `data-architecture.md` | Data view | Какие данные существуют, где хранятся, как текут между компонентами, каков их жизненный цикл |
| `network-architecture.md` | Network/trust-boundary view | Кто с кем говорит по сети, по какому протоколу, где граница доверия |
| `runtime-view.md` | Runtime view (4+1) | Как компоненты взаимодействуют во времени на конкретных сценариях (диаграммы последовательности) |
| `state-view.md` | Behavioral view | В каких состояниях находятся ключевые сущности и как переходят между ними |
| `security-view.md` | Security view | Эшелоны защиты и границы доверия на одной картинке, а не только таблицей |
| `quality-attributes.md` | Quality view (arc42 §10) | Какие нефункциональные требования система обязана выполнять и как это проверяется |
| `domain-glossary.md` | Domain view | Единый словарь понятий и их связи (ubiquitous language) |
| `risks-and-debt.md` | Risk view (arc42 §11) | Что осознанно принято как компромисс/риск и что ещё открыто |

## Зачем эти семь сверх запрошенных четырёх

Системная, компонентная, данных и сетевая архитектуры описывают *структуру*. Без представления *поведения во времени* (runtime, state) читатель не увидит, как структура на самом деле работает под нагрузкой и при сбое — а именно там живут инварианты I2/I6/I7. Security view переупаковывает уже существующую таблицу угроз в картинку, потому что эшелонированность (L0–L8) — пространственное свойство, которое таблица передаёт хуже диаграммы. Quality attributes и risks-and-debt — стандартные разделы arc42, без которых архитектурный пакет не даёт ответа на «а как проверить, что это вообще работает» и «что мы сознательно не решили». Domain glossary фиксирует словарь до того, как разные части кода начнут называть одно и то же по-разному.
