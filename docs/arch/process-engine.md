# Process Engine — спецификация детерминированного остова

> Спецификация компонента. См. `ideal-agent-architecture.md` §3.1. Самодостаточна: все используемые понятия описаны здесь или в главном документе.

## 1. Назначение

Process Engine — единственный способ выполнения структурированных задач. Он заменяет свободный агентный цикл там, где задача декомпозируется заранее, а это большинство прикладных задач. Свободный агентный цикл остаётся, но только как шаг типа `agent_step` или явный пользовательский режим.

## 2. Модель процесса

Процесс — направленный граф шагов, описанный декларативно и компилируемый в исполняемый граф при загрузке. Модель версионируется; хэш версии записывается в каждое событие выполнения, чтобы любой прогон можно было воспроизвести и отнести к конкретной редакции процесса.

**Привязка версии:** инстанс процесса фиксирует версию графа в момент `instantiate` и выполняется на ней от начала до конца, включая восстановление после сбоя (§4) — публикация новой версии не меняет поведение уже запущенных инстансов. Сосуществование инстансов на разных версиях — нормальный режим, не рассинхронизация. Перевод работающего инстанса на новую версию — отдельная операция `migrate_version`: требует подтверждения человека (I2) и проверки текущего состояния против схемы новой версии; без явного вызова этой операции миграции не происходит.

Пример декларативного описания:

```yaml
process: card-delivery-support
version: 3
steps:
  - id: classify
    type: llm_structured
    contract: ClassificationOut      # ссылка на схему данных
    model_tier: any
  - id: check_risk
    type: branch
    on: state.classify.risk
    cases:
      ">=7": human_review
      "<7":  fetch_card_status
  - id: human_review
    type: human_gate
    reason: "высокий риск: {{state.classify.risk}}"
  - id: fetch_card_status
    type: tool
    tool: crm.get_card_status
    args: {id: "{{state.user.card_id}}"}
  - id: answer
    type: llm_structured
    contract: SupportReply
limits:
  max_steps: 50
  timeout: 10m
  token_budget: 100k
```

### Типы шагов

| Тип | Семантика | Участвует ли модель |
|-----|-----------|---------------------|
| `sequential` | композиция, переход по порядку | нет |
| `parallel` | веер шагов, join по барьеру | нет |
| `loop` | итерация до условия; условие — код | нет |
| `branch` | ветвление по валидированным полям состояния | **никогда** |
| `tool` | один вызов инструмента; аргументы — шаблон из состояния | нет |
| `llm_structured` | модель + контракт схемы (через Mediation) | да, узко |
| `codeact` | модель пишет программу, изолированное выполнение, логи в состояние | да, изолированно |
| `agent_step` | свободный цикл «рассуждение-действие» с лимитом ходов | да, ограниченно |
| `human_gate` | обязательное решение человека | нет |
| `checkpoint` | явный снапшот (неявно — перед каждой мутацией) | нет |

Набор типов намеренно ограничен. Малый композируемый набор тестируется целиком: для каждой комбинации типов можно написать контрактные тесты. Произвольный граф, дорисовываемый на ходу, тестированию не поддаётся — поэтому выразительность приносится в жертву предсказуемости.

### Контракты из конфигурации (0.28.0)

`llm_structured`, `codeact` и `agent_step` (финальный результат) принимают не только контракты, скомпилированные в бинарник, но и объявленные оператором в конфиге — секция `[[contracts]]` с JSON Schema (inline `schema` или `schema_path` относительно файла конфига). Загрузка: имя уникально и не совпадает с кодовыми, схема компилируется (`jsonschema::validator_for`) — ошибка = конфиг не грузится. Исполнение: lookup по имени сначала в кодовом реестре, затем в конфигурационном; generic-медиация — разбор JSON из ответа модели → валидация по схеме → контроль утечек секретов → патч в `state.<step_id>`; ошибка валидации уходит в промпт повтора (та же таблица Retry/Escalate). Осознанные ограничения против кодовых контрактов: нет policy-правил (ссылки на состояние не проверяются), нет версий схем, `publishable` — весь объект, реестр читается один раз при старте (смена конфига — новый запуск). Пример — `fixtures/golden/processes/config-contracts/`.

**Поля-обоснования (SGR, 0.30.0).** Контракт может вести рассуждение модели: поля-обоснования объявляются ДО целевых — `risk_factors` (непустой список) перед `risk` в `ClassificationOut` (версия схемы 2). Порядок полей в JSON Schema соответствует порядку объявления (schemars собран с `preserve_order`; без него `properties` сортировался алфавитно и порядок терялся). Принуждение порядка генерации — `response_format` в `[[providers]]`: `none` | `json_object` | `json_schema` | `grammar` (не задано — вывод из `json_object_response_format`). `json_schema`: схема контракта уходит в поле запроса (OpenAI-совместимые, strict) или в `format` (Ollama) — модель физически генерирует поля в порядке схемы. Провайдеры без constrained decoding (DeepSeek, Kimi — только `json_object`, проверено живым вызовом 2026-08-14) получают мягкий уровень: порядок в промпте + обязательность полей по схеме + валидация медиации. Это подсказка транспорту, не гарантия — принятие ответа всегда решает медиация.

## 3. Состояние

- **Состояние** — иммутабельный документ в журналируемом ключ-значение хранилище. Шаг получает read-view и возвращает **патч** (декларативное описание изменения), движок применяет его атомарно.
- **История** — каждый патч = событие `step.applied` в журнале. Воспроизведение: новое состояние = свёртка патчей — детерминированно, без моделей.
- **Изоляция:** шаг не видит ничего, кроме состояния и объявленных входов; обращение к чужим сессиям невозможно типом интерфейса.
- **Гейт валидации:** патч от `llm_structured`, `codeact`, `agent_step` проходит контрактную валидацию до применения (см. `mediation.md`).

## 4. Выполнение

```
instantiate(process, input) → цикл:
  step  := graph.next(state)                  # код, не модель
  ctx   := context_engine.build(step, state)  # код
  out   := executor.run(step, ctx)            # structured / codeact / tool
  patch := mediation.commit(step, out)        # контракт + политика
  state := state.apply(patch)
  emit(step.applied{process, version, step, patch_hash})
  snapshot() if step.mutates
  next  := graph.eval(state)                  # код
```

- **Отказоустойчивость:** падение процесса — не потеря работы. Следующий запуск продолжает с последнего события журнала: состояние восстанавливается свёрткой, выполнение — с первого незавершённого шага. Это исключает целый класс дефектов «задача потерялась при сбое/перезапуске». Восстановление всегда идёт по версии графа, зафиксированной в событиях самого инстанса, а не по версии, загруженной в реестре процессов на момент перезапуска.
- **Конкурентный доступ:** один инстанс процесса — один писатель состояния. Параллельные шаги пишут в разделённые неймспейсы (`state.parallel.<step_id>`), join мержит по барьеру после завершения всех ветвей.
- **Лимиты:** `max_steps`, `timeout`, `token_budget` — детерминированные прерыватели. Они же — защита от бесконечных циклов, главного эмерджентного сбоя систем с самостоятельной маршрутизацией. Опционально к ним — `cost_budget` и пошаговый `latency_budget`, отсекающие дорогих или медленных провайдеров ещё на этапе выбора моделью в Model Pool (см. `ideal-agent-architecture.md` §3.10); это тоже прерыватели процесса, а не рекомендации.

## 5. Шаг человеческого контроля и эскалация

- `human_gate` — полноценный шаг: процесс останавливается, событие уходит на поверхность (карточка подтверждения в интерфейсе), ответ возобновляет выполнение.
- **Эскалация детерминированная:** заданное число ошибок валидации, класс модели ниже порога для шага, риск-поле контракта выше порога, таймаут шага. Пути «модель решила спросить человека» не существует.
- Таймаут ожидания человека — политика процесса: падение шага, ветка по умолчанию или эскалация выше. Явно, не молчаливо.
- **Предел очереди подтверждений — системный, не за счёт шага.** Число одновременных `human_gate`-остановок на арендатора/очередь ограничивает диспетчер (см. `ideal-agent-architecture.md` §3.8), а не движок отдельного процесса: при достижении предела диспетчер прекращает назначать акторам новые задачи, ведущие к эскалации, до разбора очереди человеком — код-правило, не решение модели. Расписания `Scheduler`, упирающиеся в неразобранные `human_gate`, получают статус `throttled`, а не отменяются и не продолжают тикать вхолостую.

## 6. Связь с остальными компонентами

| Компонент | Интерфейс |
|-----------|-----------|
| Context Engine | `build(step, state)` — правила по типу шага, фиксированный порядок слоёв, бюджет по классу модели |
| Executors | `llm_structured → StructuredLLM`, `codeact → CodeAct`, `tool → ToolRuntime` |
| Mediation | валидация патча от любого шага с моделью до commit |
| Capability | deny/подтверждение перед мутирующими вызовами инструментов |
| Actors/Scheduler | инстанс процесса = задача актора; диспетчер назначает по правилам |
| Memory | завершение процесса → дедупликация → эпизодическая запись |

## 7. Тестирование

- **Контрактные тесты процесса:** золотой набор входов → ожидаемые ветки. Шаги с моделью заменяются фикстурами контрактов — тест не зависит от модели вообще.
- **Свойство движка (property-тест):** для любого прогона свёртка журнала событий равна живому состоянию.
- **Внедрение сбоев (fault injection):** остановка между любыми двумя шагами → продолжение не теряет и не дублирует шаги.
- **Офлайн-оценка:** метрики веток (доля человеческого контроля, доля отказов валидации) на золотом наборе до выката новой версии процесса.

## 8. Чего движок не делает

- Не выбирает процесс по запросу пользователя — это маршрутизатор: код-правила на классе задачи.
- Не планирует — план есть сама модель процесса, написанная человеком или утверждённая через контур здоровья навыков (событие + подтверждение).
- Не адаптирует граф на лету по совету модели — версия меняется только через событие и подтверждение (инвариант I2).
