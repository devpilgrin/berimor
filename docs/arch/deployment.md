# Deployment & Update — спецификация развёртывания, обновления и доверенных плагинов

> Спецификация компонента. См. `ideal-agent-architecture.md` (инварианты I1–I8) и `security-model.md`.
> В отличие от остальных документов `arch/`, этот документ называет конкретные технологии распространения (npm, GitHub) — раздача агента и его расширений неотделима от конкретного реестра пакетов и хост-платформы репозиториев. Принципы (кто решает, где верификация, где нужно подтверждение человека) при этом те же, что и в остальной архитектуре, — ничего параллельного не вводится.

## 1. Назначение и принципы

Агент распространяется как npm-пакет (тонкий bootstrap), самостоятельно определяет ОС/архитектуру, обновляет себя и устанавливает плагины из GitHub-репозиториев по доверенному списку. Перенесённые без изменений принципы:

- **I1** — что устанавливать и обновлять решает код (версия, доверенный список, политика канала), не сам агент по собственной инициативе и не эвристика «выглядит легитимно».
- **I2** — расширение доверенного списка, смена канала обновлений, установка нового плагина — событие и подтверждение человека, никогда молчаливо.
- **I4** — секреты пайплайна (токены публикации, ключи подписи) не живут на машинах разработчиков и недоступны рантайму агента.
- **I6** — недоверенный или неверифицированный артефакт блокируется статически до исполнения; ошибка верификации не преодолевается подтверждением.
- **I7** — каждое обновление и установка плагина воспроизводимы: журнал фиксирует источник, версию, хэш, результат верификации.

## 2. Слои распространения

| Слой | Что это | Где живёт |
|---|---|---|
| **Bootstrap-пакет (npm)** | Минимальный установщик: определение платформы, чтение доверенного списка, оркестрация само-обновления | npm-реестр, фиксированное имя, dist-tag на канал |
| **Платформенный артефакт** | Собранный под конкретную ОС/архитектуру исполняемый агент | GitHub Releases того же репозитория, не npm-реестр |
| **Доверенный список репозиториев** | Локальный журналируемый документ: разрешённые источники обновлений и плагинов | встроенные значения по умолчанию в bootstrap-сборке + локальные подтверждённые добавления |
| **Плагины** | Изолированные процессы-коннекторы (см. `ideal-agent-architecture.md` §3.9) | GitHub-репозитории из доверенного списка |

Почему платформенный бинарник — не сам npm-пакет: npm-реестр не рассчитан на раздачу тяжёлых сборок сразу под все ОС, а нужная версия известна только после определения платформы — до этого момента тянуть всё для всех бессмысленно. Bootstrap остаётся маленьким и одинаковым для всех, вариативность — только на шаге само-обновления.

## 3. Определение платформы и разрешение артефакта

- При первом запуске bootstrap определяет ОС и архитектуру процессора кодом (без эвристик по окружению) и вычисляет имя ожидаемого артефакта по фиксированному соглашению (`agent-<version>-<os>-<arch>.tar.gz`, рядом — файл подписи и файл контрольной суммы).
- Результат определения кэшируется в локальном состоянии; повторное определение — только при явном запуске диагностики, не на каждый старт.
- Неизвестная комбинация ОС/архитектуры — не попытка «угадать ближайшую», а явный отказ с сообщением и остановкой на этом шаге: попытка запустить артефакт для чужой платформы — источник неопределённого поведения, а не мелкая неточность.

## 4. Доверенный список: формат, чтение, изменение

Запись доверенного списка:

```
repo:              owner/name
allowed_ref:        semver-паттерн тегов (например "v*.*.* без пререлизов")
signer_identity:     закреплённый идентификатор подписанта релиза (открытый ключ или привязка к CI-workflow репозитория)
capability_ceiling:  максимальный ACL, который артефакт из этого репозитория может получить без дополнительного подтверждения
added_by / added_at / event_id: происхождение записи
```

- **Доверие к репозиторию ≠ доверие к любому будущему артефакту вслепую.** Запись в списке разрешает *проверять* артефакты этого репозитория без подтверждения на каждый релиз — но каждый артефакт всё равно обязан пройти верификацию подписи по `signer_identity`. Список не заменяет проверку, а определяет, для кого проверка вообще выполняется.
- **Изменение списка — событие, не сетевой эффект.** Добавление или удаление записи показывается человеку как diff и требует подтверждения (I2) прежде чем применяется к состоянию; источник предложения (пользователь, организация, обновление конфигурации) не имеет значения — применяет только подтверждение.
- **Запрос на расширение `capability_ceiling`** для уже доверенного репозитория — отдельное подтверждение, не входит в исходное доверие репозиторию: доверить источник обновлений — не то же самое, что заранее выдать любые будущие права.
- Список — часть журналируемого локального состояния (тот же KV-журнал, что и остальная память системы, I5): изменение без соответствующего события — расхождение, обнаруживаемое при загрузке сверткой журнала.

## 5. Само-обновление как процесс

Само-обновление и установка плагина — не отдельная неконтролируемая логика, а обычный процесс `Process Engine` (см. `process-engine.md`), что даёт ему бесплатно снапшоты, восстановление после сбоя и контрактные тесты:

```yaml
process: agent-self-update
version: 1
steps:
  - id: check_version
    type: tool
    tool: registry.get_latest      # чтение dist-tag канала, без исполнения чего-либо
  - id: needs_update
    type: branch
    on: state.check_version.version > state.local.version
    cases:
      "false": done
      "true":  major_gate
  - id: major_gate                 # мажорная версия — обязательное подтверждение
    type: branch
    on: state.check_version.is_major_bump
    cases:
      "true":  human_review
      "false": resolve_artifact
  - id: human_review
    type: human_gate
    reason: "обновление меняет мажорную версию: {{state.local.version}} → {{state.check_version.version}}"
  - id: resolve_artifact
    type: tool
    tool: platform.resolve_asset   # см. §3
  - id: download
    type: tool
    tool: github.download_release_asset
  - id: verify
    type: tool
    tool: crypto.verify_signature  # против signer_identity доверенного списка
  - id: verify_gate
    type: branch
    on: state.verify.ok
    cases:
      "false": fail_update         # без повтора — ошибка верификации не лечится повтором (I6)
      "true":  checkpoint_current
  - id: checkpoint_current
    type: checkpoint
  - id: swap
    type: tool
    tool: fs.atomic_replace_binary
  - id: smoke_test
    type: tool
    tool: agent.self_check         # запуск нового бинарника в изолированном режиме
  - id: smoke_gate
    type: branch
    on: state.smoke_test.ok
    cases:
      "false": rollback
      "true":  commit_update
  - id: rollback
    type: tool
    tool: fs.restore_from_checkpoint
  - id: commit_update
    type: tool
    tool: registry.record_version
limits:
  max_steps: 12
  timeout: 5m
```

Ни один шаг не типа `llm_structured`/`codeact`/`agent_step` — обновление целиком детерминировано, модель в этом процессе не участвует вообще.

## 6. Установка плагина

Тот же каркас, с двумя отличиями от само-обновления:

1. После `verify` — обязательный `human_gate`, если репозиторий плагина новый для доверенного списка (установка плагина — расширение прав по определению, opt-in согласно `security-model.md` §3), либо если манифест плагина запрашивает ACL за пределами `capability_ceiling` записи.
2. Финальный шаг — не замена бинарника агента, а размещение плагина в изолированной директории и регистрация его манифеста (события, доступ к секретам) в реестре ACL плагинов (`security-model.md` §4) — сам плагин не может переопределить собственный манифест.

Плагин, прошедший установку, запускается как изолированный процесс с межпроцессным RPC (`ideal-agent-architecture.md` §3.9); capability-гейты проверяют каждый его вызов независимо от того, что заявлено в манифесте.

## 7. Пайплайн сборки

| Стадия | Содержание |
|---|---|
| 1. Статика | линт, аудит зависимостей, сканирование секретов в коммите |
| 2. Модульные тесты | без сети, без реального реестра |
| 3. Контрактные тесты | золотой набор для `agent-self-update` и установки плагина — фикстуры вместо реального GitHub/npm, включая фикстуры повреждённой подписи и понижения версии (см. `process-engine.md` §7) |
| 4. Кросс-платформенная сборка | матрица ОС × архитектура, платформенные артефакты + SBOM на каждый |
| 5. Подпись | короткоживущие CI-credentials, закреплённая идентичность подписанта (workflow-привязка, не файл приватного ключа на диске разработчика) — I4 распространяется на пайплайн, не только на рантайм |
| 6. Провенанс | атрибут провенанса на npm-пакет и контрольные суммы + подписи на GitHub Release, проверяемо связывающие артефакт с конкретным коммитом и workflow-запуском |
| 7. Публикация | npm-реестр (bootstrap, dist-tag канала) + GitHub Releases (платформенные артефакты, подписи, changelog из истории коммитов) |
| 8. Поэтапный роллаут | canary → beta → stable; продвижение между каналами — код-правило по метрикам окна наблюдения (см. §9), не разовое решение человека, кроме финального продвижения мажорной версии в stable — оно как и `major_gate` в §5 требует подтверждения |

## 8. Пайплайн тестирования обновления и установки

Кроме обычных тестов кода, конвейер целится в отказы, специфичные для самообновляющейся системы:

- **Внедрение сбоев:** прерванная загрузка, усечённый артефакт, неверная контрольная сумма, неверная подпись, попытка понижения версии, подделанный доверенный список — во всех случаях обновление должно отказать закрыто: текущая рабочая версия остаётся активной, событие пишется, частичного состояния не остаётся.
- **Свойство восстановления:** для любой точки прерывания процесса `agent-self-update` повторный запуск продолжает с последнего события журнала и не повреждает установленный бинарник — то же свойство, что и для любого процесса `Process Engine` (§7 `process-engine.md`).
- **Защита от понижения версии:** источник, сообщающий версию ниже уже установленной как «последнюю», отклоняется без исключений, кроме явного подтверждённого события отката.
- **Сухой прогон на публикации:** каждый релиз перед продвижением в стабильный канал устанавливается и проходит `smoke_test` в чистом окружении по всей платформенной матрице — то же самое, что `smoke_test`-шаг воспроизводит на машине пользователя, но на стороне CI это происходит раньше, до того как артефакт вообще становится доступен по каналу.

## 9. Модель угроз распространения

Дополняет таблицу угроз `security-model.md` §1 применительно к дистрибуции:

| Угроза | Механизм | Защита |
|---|---|---|
| Компрометация аккаунта публикации | похищенный токен публикует вредоносную версию | публикация только из CI по временной идентичности workflow, долгоживущих токенов на машинах разработчиков нет; провенанс проверяемо привязывает пакет к коммиту |
| Подмена артефакта GitHub Release | загруженный бинарник заменён при сохранении имени файла | верификация по `signer_identity` из доверенного списка, а не по имени файла или самому факту скачивания с ожидаемого домена |
| Понижение версии (downgrade) | навязывание уязвимой более старой версии как «последней» | сравнение только по возрастанию semver, журнал уже применённых версий, откат — только подтверждённое событие |
| Подделка доверенного списка | локальная правка файла в обход подтверждения | список — часть журналируемого состояния (I7); расхождение со сверткой событий обнаруживается при загрузке |
| Вредоносный `postinstall` npm-пакета | код выполняется при `npm install`, до какой-либо верификации | bootstrap не выполняет ничего, кроме определения платформы, на этапе установки; скачивание и верификация — на первом запуске, тем же конвейером, что у обновлений |
| Плагин запрашивает права шире заявленных | манифест декларирует одно, вызовы во время работы — другое | ACL манифеста статичен, capability-гейты проверяют каждый вызов независимо от манифеста (`security-model.md` §4) |

## 10. Каналы, откат, наблюдаемость

- **Каналы** (`stable` / `beta` / `canary`) — локальная настройка пользователя, читаемая bootstrap'ом; переключение канала — явное действие, не решается кодом автоматически.
- **Откат:** последние N рабочих версий сохраняются локально как чекпоинты (тот же механизм снапшота, что и в `process-engine.md`); откат — явная команда или автоматическое следствие проваленного `smoke_test` (§5), никогда тихая замена без события.
- **Телеметрия:** попытки обновления, отказы верификации, откаты пишутся в тот же журнал событий и подаются в контур здоровья (`ideal-agent-architecture.md` §3.11) — рост доли отказов верификации после конкретного релиза читается как сигнал о компрометации пайплайна, тем же способом, что рост отказов Mediation читается как деградация модели.

## 11. Чего пайплайн не делает

- Не устанавливает плагин из репозитория, не бывшего в доверенном списке ранее, без подтверждения человеком.
- Не понижает версию без явного подтверждённого события отката.
- Не исполняет код артефакта до завершения проверки подписи и контрольной суммы.
- Не хранит секреты публикации вне CI и не передаёт их в рантайм агента.
- Не применяет изменение доверенного списка, пришедшее по сети, без остановки на подтверждение — сеть может предложить изменение, но не может его закоммитить.
