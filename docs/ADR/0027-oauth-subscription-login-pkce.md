# ADR-0027: OAuth-логины по подпискам (PKCE) вместо только-API-ключей

**Статус:** Принято (дизайн; реализация — §20.25 ROADMAP)
**Дата:** 2026-08-06

## Контекст

Berimor подключает провайдеров исключительно API-ключами (пресеты в
мастере, `secrets.env`). Значительная часть пользователей платит за
подписки (Claude Pro/Max, ChatGPT Plus/Pro), а не за API — для них
требование API-ключа означает вторую оплату или отказ от инструмента.
jcode (сравнение 2026-08-06) покрывает это OAuth-логинами
(`login --provider claude|openai|…`) — самая болезненная UX-разница.

Ограничения проекта: I4 (секреты — в реестре, маскировка на границах),
I5 (нет обязательных внешних сервисов — OAuth-логин опционален,
API-ключи остаются полноценным путём), детерминизм (token lifecycle —
кодом, не моделью).

## Решение

PKCE flow (RFC 7636) с loopback-редиректом (`http://127.0.0.1:<порт>/callback`),
без открытия браузера принудительно — URL печатается, браузер открывается
по возможности (`open`/`xdg-open`/PowerShell `start`), ручной ввод кода —
резервный путь для headless.

1. `berimor login --provider claude|openai` — PKCE state/challenge,
   loopback-listener, обмен кода на токены, запись в реестр секретов
   (`secrets.env`-совместимый файл, права 0600 — та же граница I4).
2. Refresh — кодом при 401/expired, без участия модели: прозрачный
   слой в HTTP-провайдере (один класс ошибок — один путь обновления),
   с журнальным событием обновления (без значений токенов).
3. Провайдер OAuth — отдельный тип записи в конфиге рядом с
   API-key-провайдером; failover между ними — существующий Model Pool.

## Альтернативы

- **Device Authorization Grant (RFC 8628)** — отклонено для v1: Claude и
  OpenAI subscription-flows построены на authorization-code + PKCE;
  device flow у этих провайдеров не поддержан. Может появиться вторым
  шагом для провайдеров, где он есть.
- **Хранение refresh-токена в системном keyring** — отклонено: I5
  (keyring — внешний сервис, на headless-серверах его нет), а граница
  `secrets.env` 0600 уже доказана и переносима.
- **Проксирование через сторонний OAuth-агрегатор** — отклонено
  категорически: токены подписки пользователя не покидают его машину
  никуда, кроме эндпоинтов самого провайдера.

## Последствия

Пользователь подписки получает полноценный вход без API-расходов.
Refresh-токен — секрет длительного действия в периметре I4: компрометация
`secrets.env` теперь означает и компрометацию подписки, что поднимает
требования к маскировке (уже покрыта) и к `trust`-гигиене каталога
конфигурации. Отзыв — `berimor logout --provider …` (удаление записи +
best-effort revoke у провайдера).

## Тесты (стратегия §20.25)

Мок token-endpoint'ов локальным HTTP-сервером: полный PKCE state-machine
(verifier→challenge→обмен), refresh при истёкшем access, отказ при
невалидном state, отзыв. Без реальных аккаунтов в CI — ручной чек-лист
на живых подписках, помечен manual.
