## 1. Ядро: process-engine, mediation, types

### HIGH

**1.1. Движок игнорирует `patch.step_id` исполнителя при журналировании, но использует при применении — молчаливое нарушение I7.**
`engine.rs:330-339`: событие пишется как `StepApplied{step_id: <id из графа>}` с payload `patch.changes`, а `state::apply_patch` кладёт изменения под `patch.step_id`. Исполнитель, вернувший patch с чужим `step_id`, навсегда рассинхронизирует живое состояние и свёртку журнала. Прогон: `step_id: "classify_FORGED"` → live keys `["classify_FORGED"]`, folded keys `["classify"]`, ни одной ошибки от движка.

**1.2. Подделка parallel-барьера пользовательским входом.**
`graph.rs:275-281` + `state.rs:81-91`: неймспейс `state.parallel.<fork>.<branch>` не изолирован от входа. `Instantiated` сидирует вход на верхний уровень состояния без фильтрации, а `parallel_branch_done` считает ветвь выполненной по факту наличия ключа. Вход `{"parallel": {"fanout": {"branch_a": 1, "branch_b": 2}}}` → прогон: 0 `ParallelStepApplied`, исход `Finished`, исполнитель ни разу не вызван.

**1.3. `on_timeout: {action: branch, to: X}` никогда не исполняет целевой шаг.**
`engine.rs:459-464`: политика присваивает `current_step = Some(to)`; семантика `current_step` — «последний посещённый», поэтому следующий `run()` идёт ПОСЛЕ `to`. Прогон: fallback-шаг типа `tool` → `Finished`, `state == {}`, `StepApplied{fallback}` в журнале отсутствует. Тест крейта этого не видит (цель там `sequential` без продолжения).

**1.4. «Пауза» human_gate фиктивна: любой повторный `run()` продолжает процесс мимо гейта.**
`engine.rs:456-466`: после политики таймаута `escalate` (и даже `fail`, ошибка `HumanGateTimeout` выдана!) `current_step` остаётся на `human_gate`, а `next_step` для него — обычный passthrough. Прогон: escalate → `run()` → `Finished`, `state.after` записано. Doc-комментарий `:422-424` («инстанс остаётся на паузе») неверен. Принуждение I2 держится только на дисциплине вызывающего кода (CLI сам пишет `HumanGateResolved`; ядро не проверяет).

**1.5. Утечка секрета неотличима от нарушения политики по типу исхода медиации.**
`pipeline.rs:70-91`: обе ситуации → `MediationOutcome::Escalate { escalated_from: Policy, reason: String }`. Спека `mediation.md` §5 требует для утечки «падение процесса + событие безопасности», для политики — «эскалация человеку»; вызывающий код может различить их только сравнением строки. Следствие: `EventKind::SecurityEvent` не производится нигде в системе (grep: только определение и чтение в eval).

### MEDIUM

**1.6.** `state.rs:45-67` + `graph.rs:74-119` — `compile` не запрещает шаг с id `parallel`: его патч стирает весь неймспейс барьера вместе с результатами выполненных ветвей (прогон: результат `branch_a` утрачен и в live state, и в свёртке).

**1.7.** `engine.rs:96-115` — `instantiate` не проверяет непустоту журнала: повторный `instantiate` с тем же id дописывает второй `Instantiated`, `fold` пересидирует состояние ПОСЛЕДНИМ входом (прогон: `fold = {"a":2,"b":3}` — первый вход потерян).

**1.8.** `engine.rs:132-161` — `recover` несуществующего инстанса возвращает `Ok` с пустым «призраком»; первый `StepApplied` после этого попадёт в журнал без `Instantiated` — ровно тот дефект, который `Instantiated` был введён исправить (`event.rs:62-65`).

**1.9.** `types/step.rs:119-165` — `Step`/`Process`/`ProcessLimits` без `deny_unknown_fields`: `token_budjet: 100k` → `token_budget: None`, `modle_tier: strong` → `Any` — молча. Для контрактов медиации `deny_unknown_fields` обязателен (§4.2), для процессных деклараций (лимиты, класс модели) та же угроза не закрыта.

**1.10.** `mediation/telemetry.rs:24-34` — `outcome_to_event_kind` никогда не производит `MediationParsed`/`MediationValidated`, хотя `mediation.md` §2 требует «каждая стадия пишет событие»; мёртвые варианты публичного контракта + «доля отказов» из журнала недостижима в точной форме.

**1.11.** `instance_lock.rs:1-16` — doc обещает защиту от «двух процессов CLI», реализация — `Arc<Mutex<HashSet>>` в памяти одного процесса. Межпроцессный случай не закрыт вообще: два CLI продублируют события одного инстанса.

**2.4.** `deny.rs:651-664` — символический setuid через комбинированные флаги: `chmod u+sx`, `chmod a+xs`, `chmod u=s`, `chmod =s` → ALLOW (контроль `chmod 6755` → DENY).

## 3. Исполнители, model-pool, CLI, codeact-guest

### HIGH

**3.1. Белый список CodeAct обходится через `this`, а сужения инструментов шага в рантайме не существует вообще.**
`static_analysis.rs:196-204` + `executor.rs:21-32` + `tool_only.rs:90-117`: `ReferenceChecker` проверяет только идентификаторы; `this` на верхнем уровне — `ThisExpression`, и в госте `this === globalThis`. Любой заблокированный глобал доступен как `this.eval`, `this.Function`, `this.Date`. `host_call_tool` (`wasm_host.rs:367-442`) не проверяет имя инструмента против `tools` шага. Прогон: `SA this.eval: Ok(())`; `B2: dispatch saw: ["secret_tool"]` при анализе с `tools=[]`; `C3: this.Function(...) → dispatch saw: ["via_Function"]`. «Двойная линия обороны» из doc — фактически отсутствует; реальные рубежи сегодня: структурная изоляция WASM (подтверждена) и capability-гейт.

**3.2. `finish()` в госте не терминален: эффекты после «выхода» исполняются, исключение после `finish` уничтожает записанный результат.**
`codeact-guest/main.rs:154-199`: `finish` лишь пишет в ячейку, исполнение продолжается. Прогон: `finish(r); call_tool('x',{})` → побочный эффект после «выхода», результат коммитится; `finish(r); throw …` → `GuestFailed`, корректный результат потерян; `finish({a:1}); finish({b:2})` → побеждает последний. Спека executors.md §4.2: «единственный выход — функция финального ответа».

**3.3. CodeAct-запрос к HTTP-провайдеру шлёт `response_format: json_object` для запроса JS-программы.**
`codeact/executor.rs:138-142` × `http_provider.rs:139-141`: `contract_name: Some(...)` мапится в принудительный JSON-режим сервера; реальный endpoint заставит модель ответить JSON вместо JS → все 3 попытки сгорают, `AttemptsExhausted`. codeact-шаг структурно неработоспособен через единственный реальный провайдер Milestone 1. По чтению (нужен живой endpoint), механика — часть OpenAI-спеки.

**3.4. `http_provider.rs:48-52` — ни одного таймаута.**
`Client::builder().build()` без `.timeout()`: зависший endpoint блокирует `berimor run` навсегда (blocking-клиент, синхронный цикл; лимиты CodeAct снаружи песочницы не помогают).

**3.5. `main.rs:107-120` — `berimor verify`, `plugin install`, `self-update` печатают «todo» и завершаются с exit code 0.**
ADR-0025 предписывает bootstrap-слою вызывать `berimor verify` для криптопроверки — автоматика получит ложное «подпись валидна». Прогон: `berimor verify some-artifact` → `todo(ROADMAP D2)`, `exit=0`.

### MEDIUM

**3.6.** `Math` в `SAFE_GLOBALS` + `this.Date.now()` — недетерминизм внутри «детерминированного ядра» (прогон: `Math.random` 0.5685 vs 0.8889 на двух одинаковых прогонах; `this.Date.now()` → реальное время). Replay по журналу (§3.11) воспроизводимость теряет.
**3.7.** Результат >1 МиБ роняет гостя паникой (`panic=abort` в `stdio::_print`), хост получает нечитаемый `Trap` с wasm-бэктрейсом — в retry-фидбек модели уезжает дамп (прогон B9).
**3.8.** Рассинхрон диалектов: анализатор парсит как ES-модуль (`SourceType::mjs()`), гость исполняет как скрипт → статический `import` принимается анализом и гарантированно падает в рантайме; `ImportDeclaration` не проверяется вообще (латентная дыра при будущем eval-модуля).
**3.9.** `http_provider.rs:157-159` — тело ответа читается целиком без size-cap → исчерпание памяти от сломанного/злонамеренного endpoint'а.
**3.10.** `config.rs:161-170` — отсутствующий ЯВНО указанный `--config` молча заменяется дефолтами: опечатка в пути = молчаливая смена security-режима (smart вместо off, потеря провайдеров).

### LOW

**3.11.** Самодельный разбор URL в гейте (`http_provider.rs:68-83`): `http://user:pass@host/` → гейт проверяет хост `"user"`; гейт и соединение проверяют разные хосты (класс SSRF-обхода). По чтению.
**3.12.** `unreachable!` (`structured_llm.rs:243`, `agent_step.rs:320`) опирается на инвариант чужого крейта (MAX_RETRIES=2 vs MAX_ATTEMPTS=3) — связка констант ничем не скреплена.
**3.13.** `agent_step.rs:300-301,404-405` — `expect` на round-trip `patch.changes → AgentTurnDecision` (паника при расхождении схемы после рефакторинга).
**3.14.** `--resume` молча игнорирует `--input` (`run.rs:88-109`).
**3.15.** MCP-инструмент молча затеняет статический `tool_stub` с тем же именем (`mcp_dispatch.rs:197-204`).
**3.16.** Отказ человека на human_gate → exit code 1, неотличим от сбоя (`run.rs:203`).
**3.17.** `let _ = storage.append(...)` для телеметрии/HumanGate-событий (`run.rs:120-126,190-197`) — отказ журнала молча теряет аудит-след (security-model §5).
**3.18.** `classify_trap` по подстроке «fuel» (`wasm_host.rs:306-319`); `Engine`+`Module` компилируются на каждый `run()` (~60-80 мс); ошибка `set_fuel` мапится в неверный вариант `Compile`; мёртвый параметр `new_instance_id` (`run.rs:543-545`); doc гостя «call_tool не бросает» неверен для несериализуемых аргументов (прогон C6).

**Проверено и дефектов НЕ найдено:** WASI deny-by-default реален (пустой `WasiCtxBuilder`); у гостя нет std/os-модулей QuickJS; `read_guest_utf8` проверяет `ptr+len` до аллокации; `max_tool_calls` грациозен; топливо трапит; `StoreLimits` подтверждён; отказ capability-гейта не обходится; бесконечных циклов без лимита в agent_step нет; сбой диспетча → наблюдение (фикс E9 на месте); API-ключ в логи/ошибки не утекает.

## 4. Память, хранилище, актёры, eval, context-engine

### HIGH

**4.1. `Dispatcher`: счётчик `open_escalations` рассинхронизируется со статусами задач — два вектора, один корень.**
`dispatcher.rs:207-235`: `open_escalations` обновляется только в `record_failure` (вставка) и `resolve_escalation` (удаление).
- а) `record_success` на эскалированной задаче не снимает её из счётчика: задача `Done`, а очередь human_gate навсегда «полна» → все новые назначения блокируются `HumanGateQueueFull`. Прогон: после `record_success` `open_escalations_count = 1`, назначение новой задачи → `Err`.
- б) `record_failure` на эскалированной задаче молча деэскалирует её в `Failed{attempts:1}` (статус матчится `_ => 1`), счётчик при этом остаётся: эскалированная задача снова назначаема (обход §3.8 «не назначается акторам снова»), а место в очереди занято призраком. Прогон подтвердил оба.

**4.2. Роутер контекста не знает `agent_step`/`codeact` — модель этих шагов получает пустой контекст.**
`context-engine/lib.rs:46-59` × `agent_step.rs:156` × `codeact/executor.rs:122`: `layers_for_step` матчит только `"llm_structured"`, для остальных — `vec![]` с комментарием «у шагов без модели контекста нет». Но `AgentStepExecutor` и `CodeActExecutor` вызывают `context.build("agent_step"/"codeact", …)` и шлют результат модели как `system_context` — он всегда пуст: ни системных правил, ни состояния задачи, ни слоёв памяти. Роутер (C1, Milestone 1) не расширен при добавлении model-bearing шагов E7/E8. Для agent_step состояние процесса не доходит до модели вообще никаким путём.

### MEDIUM

**4.3. Бюджетная механика контекста не подключена нигде.**
`context_engine::budget_chars`/`total_chars` (C3) и `working::over_budget`/`collapse` (MEM1) не вызываются ни из одного не-тестового кода (grep по workspace). Заявленные механизмы «слабая модель получает более короткий контекст» (§3.5) и «сворачивание при переполнении бюджета» (§4) существуют только как API без потребителей.

**4.4. Валидация расписаний — только на верхнем слое; прямой `upsert_schedule` принимает невозможное расписание.**
`scheduler.rs:34-41` проверяет `interval_ms > 0`, но `SqliteEventLog::upsert_schedule` (`storage/lib.rs:744`) — нет: вызывающий, миновавший `Scheduler`, получает расписание, срабатывающее на каждом тике вечно (`interval <= 0` продвигает время назад/на месте). Дополнительно: `tick` продвигает повторяющееся расписание на ОДИН интервал за раз — после длительного простоя система «догоняет» пропущенные срабатывания штормом тиков вместо одного скачка к `now + interval`.

**4.5. Session-слой eval-стенда ищет по эфемерному журналу самого eval, а не по реальной истории.**
`observe.rs:82-92`: `MemoryContextBuilder { episodic: &storage }` получает in-memory журнал, в который пишутся события самих сценариев. Слой Session в eval находит события предыдущих сценариев того же прогона и текущего сценария (самоотсылка), но никогда — реальные прошлые сессии. Контекст сценариев взаимно загрязнён.

### LOW

**4.6. «Символы» = байты.** `working::total_chars` и `context_engine::total_chars` считают `str::len()` (байты), тогда как doc и имена говорят «символы»: для кириллицы эффективный бюджет вдвое меньше заявленного. Согласовано между модулями, расходится с документацией.

**4.7.** `semantic.rs:132-144` — `VectorSimilarity::similarity` проглатывает ошибку хранилища в `0.0` (`.ok().flatten().unwrap_or(0.0)`): повреждённое хранилище неотличимо от «факты непохожи» → молчаливые ложные `New` вместо сигнала о сбое.

**4.8.** `bus.rs:97` — `persist_envelope` не идемпотентен (plain INSERT): повторная публикация того же конверта (ретрай после транзиентной ошибки) → `StorageError` по PK вместо идемпотентного успеха.

**4.9.** `golden.rs:94` — id инстанса сценария `"{процесс}::{сценарий}"` без проверки уникальности внутри набора: два сценария с одинаковым именем (или повторный eval на неэфемерном журнале) объединят метрики. Частично смягчено эфемерным журналом в `observe.rs` (см. 4.5).

## Системные выводы

1. **Перечислительные таблицы против классов угроз.** Прошлое XL-ревью закрыло перечисленные формы, но не классы: таблицы обёрток, опций, программ-синонимов, устройств, форм chmod/chown/find/cp остались перечислительными — каждая соседняя форма того же класса проходит (находки 2.1–2.7, 2.9–2.13). То же в статическом анализе CodeAct (3.1): проверка идентификаторов не закрывает класс «доступ к глобалам не-идентификатором».
2. **Декларированные «двойные линии обороны» распадаются до одной.** CodeAct: «статический анализ + сужение инструментов» — в рантайме нет ни того, ни другого; остаются WASM-изоляция и capability-гейт. Jail: заявлен в security-model как слой, не имеет потребителей. Бюджет контекста: заявлен в §3.5, не подключён.
3. **Состояние-в-данных подделываемо входом.** Ядро доверяет пользовательскому JSON в областях, которые само же использует служебно: parallel-барьер (1.2), пересидирование через повторный `instantiate` (1.7), стирание неймспейса шагом с id `parallel` (1.6). Нужен запрет служебных ключей верхнего уровня во входе инстанса.
4. **Doc ↔ поведение расходятся на границах доверия.** «Пауза» human_gate (1.4), «deny как режим» (2.8), «единственный выход — finish» (3.2), «двойная линия обороны» (3.1), «голое число отклоняется» (1.13), обещание межпроцессного лока (1.11). Каждый случай — место, где читатель документации положится на несуществующую гарантию.
