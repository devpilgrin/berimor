### Выводы из данных

1. **Консенсус индустрии:** MCP + skills + workflows + subagents + checkpoints — ядро любой современной системы.
2. **Multi-agent есть везде, но LLM-роутинг — редко оправдан.** Anthropic прямо рекомендует начинать с workflows, а не с autonomous agents.
3. **Code actions (CodeAct, smolagents, TaskWeaver) — растущая, но ещё редкая практика (5/18).** При этом CodeAct показывает, что открытые модели конкурируют с закрытыми именно в code-as-actions режиме.
4. **Compliance-by-construction и Nubank подтверждают:** пространство действий должен задавать детерминированный код, LLM — интерпретировать неструктурированные данные внутри шага.
5. **Claude Code и Hermes сошлись на одном:** проектный контекст-файл, checkpoints, permission modes, изолированные субагенты, skills как процедурная память.

## 3. Варианты архитектуры

### Вариант A: Монолитный ReAct-агент (базовая линия Claude Code)

```
User → Agent Loop (LLM решает всё) → Tools → Observation → Loop
+ project context file, checkpoints, permission modes
```

- **Плюсы:** прост, доказан (Claude Code, Codex), максимальная гибкость на открытых задачах.
- **Минусы:** LLM — единственный роутер и планировщик; на слабой модели деградирует первым; детерминизм низкий.

### Вариант B: LLM-оркестратор + воркеры (Anthropic orchestrator-workers / AG2 Network)

```
User → Orchestrator LLM (декомпозиция, делегирование)
      ├→ Worker LLM 1 (изолированный контекст)
      ├→ Worker LLM 2
      └→ Synthesis LLM
```

- **Плюсы:** масштабируется, параллелится, изоляция контекстов.
- **Минусы:** оркестратор — это LLM-роутер, прямое нарушение принципа «слабым моделям нельзя доверять маршрутизацию»; тройной расход токенов; эмерджентные сбои координации (бесконечные циклы, блокировки — см. Springer-обзор).

### Вариант C: CodeAct-исполнитель (smolagents / TaskWeaver)

```
User → ReAct Loop → LLM генерирует Python-код → Sandbox exec → Logs → Loop
+ final_answer() завершает задачу
```

- **Плюсы:** код композитнее JSON tool-calls (меньше шагов, циклы/условия в одном действии); открытые модели (DeepSeek-R1) на паре с закрытыми именно в этом режиме; sandbox даёт безопасность.
- **Минусы:** план по-прежнему рисует LLM; нужен полноценный sandbox; отладка сгенерированного кода на слабой модели болезненна.

### Вариант D: Детерминированный процессный остов + LLM-интерпретаторы шагов (compliance-by-construction + ADK workflows + Nubank)

```
Процессная модель (Go state machine: Sequential/Parallel/Loop/Branch)
  ├→ Шаг 1: LLM интерпретирует вход → выход валидируется контрактом (Pydantic-схема/Go-struct)
  ├→ Шаг 2: Tool call (MCP), параметры — из валидированного состояния
  ├→ Шаг 3: LLM-шаг с checkpoint перед ним
  └→ Ветвление: детерминированные условия на валидированных данных
```

- **Плюсы:** полный детерминизм решений; слабая модель справляется (задача шага узка); валидация контрактов — «trust but verify»; аудит и replay из коробки; именно так работают ADK workflows, Nubank и compliance-by-construction.
- **Минусы:** открытые задачи («исследуй и придумай») в чистую процессную модель не ложатся.

## 5. Лучший вариант: гибрид D + C + A («остов-исполнитель-люк»)

Чистый D выигрывает матрицу, но проигрывает на открытых задачах. Чистые A/B/C проигрывают по главному принципу. Оптимум — композиция:

```
┌────────────────────────────────────────────────────────────┐
│ 1. ДЕТЕРМИНИРОВАННЫЙ ОСТОВ (Go)                            │
│    Процессный движок: Sequential / Parallel / Loop / Branch│
│    Состояние в Pebble, checkpoints перед мутациями         │
│    Роутинг и ветвление — ТОЛЬКО код, никогда не LLM        │
├────────────────────────────────────────────────────────────┤
│ 2. ИСПОЛНИТЕЛИ ШАГОВ                                       │
│    Узкий шаг → LLM + JSON-контракт (structured output)     │
│    Сложный шаг → CodeAct: Python в sandbox                 │
│    Выход валидируется схемой ДО записи в состояние         │
├────────────────────────────────────────────────────────────┤
│ 3. ЛЮК В АГЕНТНЫЙ РЕЖИМ (вариант A)                        │
│    Открытая задача → монолитный ReAct-loop с лимитом ходов │
│    Вход в режим — детерминирован: явный запрос пользователя│
│    или тип шага в процессной модели, НЕ решение LLM        │
├────────────────────────────────────────────────────────────┤
│ 4. СКВОЗНЫЕ СЛОИ                                           │
│    MCP — единый интерфейс инструментов                     │
│    Skills — процедурная память (markdown, on-demand)       │
│    Approvals — smart-режим, деструктивное → подтверждение  │
│    Tracing — каждый шаг с replay                           │
└────────────────────────────────────────────────────────────┘
```

### Обоснование через данные

- **Детерминированный остов** — топ-3 паттернов базы (workflows 30, plan-and-execute 24), рекомендация Anthropic «start with workflows», архитектура ADK и Nubank.
- **CodeAct внутри шагов** — единственный режим, где локальные/открытые модели догоняют закрытые (smolagents benchmark); меньше токенов на многошаговых задачах.
- **Люк в ReAct** — покрывает 20% задач, которые не моделируются процессом; решение о входе детерминировано, принцип не нарушается.
- **MCP + skills** — два самых частых паттерна базы (45 и 33), уже реализованы в Hermes и Claude Code.
- **Валидация контрактов** — compliance-by-construction: слабая модель не может «протащить» невалидный выход дальше шага.

### Отображение на Jarvis

| Компонент | Реализация |
|-----------|------------|
| Процессный движок | Go state machine, шаги как Go-интерфейсы |
| Состояние/память | Pebble: STM шага + LTM сессии, replay |
| Контракты шагов | Go-structs + schema-валидация JSON-выхода LLM |
| Sandbox CodeAct | Docker/изолированный subprocess (Python) |
| Инструменты | MCP-клиент, сервер — для внешних потребителей |
| Skills | `~/.jarvis/skills/`, загрузка описаний on-demand |
| Агентный люк | ReAct-loop с max_turns и checkpoint-per-edit |
| Approvals | smart → manual → off, как в Hermes |

### Когда что использовать

- **Задача декомпозируется заранее** → процессная модель (D). Это большинство production-задач.
- **Шаг требует вычислений/итераций по данным** → CodeAct-исполнитель (C).
- **Задача открытая, исследовательская** → агентный люк (A) с лимитом ходов и checkpoints.
- **Никогда:** LLM-роутер между агентами (B) — отклонён как нарушение базового принципа и подтверждённый источником эмерджентных сбоев.
